- 2026-10-16 A best set may copy an item it upgrades. The review of the canonical hands found that the best k additions made at once could be worth less than the first k steps of the farm path (upgrade-012 of the fixtures: the best 2 set was 13819.16 and the best 3 14225.15, against 14539.42 for step 2). The path upgrades an owned item (the same key at a lower tier) into the candidate, and a later step adds another copy of the candidate, which is a `copy` by then because the upgraded item is owned. The set model could not say that: the builder tied every wear of an upgrade's target to a copy of its source (`own.<source>` covered the target's columns), so wearing the target twice took two owned copies of the source. By the semantics of `upgrade.py` the k steps of the path are k additions, so every path of k steps must be a feasible set of k additions, and the best set of k is never worth less than step k. The rule: only the first copy of an upgrade's target is made from the owned source, one copy of it; every further copy of the target is a copy of the target, one addition each, as in the path (once the target is owned it is a copy candidate, never an upgrade again). Upgrading two copies of the source costs as many additions as one upgrade and one copy and leaves fewer of the source, so the model never needs it. In the builder (`_ownership_rows` in `model.py`, and the same in `model.js`), a target that can be worn more than once (not Lore, and the sum of the upper bounds of its columns, no more than `max_new` when that is set, above 1) has a 0/1 integer column `made[<target>]` and the row `made.<target>`: the sum of its columns less that sum times `made` is at most 0, so a worn target has `made` 1; `own.<source>` counts `made` in place of the target's columns, and every wear of the target is still one of the `max_new`. A target that can be worn once at most keeps the rows it had, so every program with one new wear, which is every program of the farm path, is the program it was, row for row and column for column. `acquired` of a best set lists each upgrade followed by the copies of its target the kit wears, then the new items, then the copies of owned items above their counts, each group by ident (it was the upgrades, the new items and the extra copies by ident, with an upgrade listed once for each wear). The owned-aware pruning reads no bound on the wears of a target from the count of its source (a source with enough copies has places for its own wears and the copy made for each worn target, so its row still never binds), and an item that replaces a target wear for wear costs no more acquisitions than the target did, so it is unchanged and its text only says that the first wear is the one that costs a copy of the source. On the fixtures made again from the same seed and data (the 19 Upgrade sessions of the full set, of which the committed sample holds 6): Equip now, the steps, why each path stopped and Every slot are the same in every session, and so is every program of Equip now and of the steps; 3 of the 38 best-set entries changed (upgrade-002 k=3, upgrade-012 k=2 and k=3), each to a higher value, and 30 of the 38 best programs have a different model (the `made` columns and rows added, 288 of each over the 30 programs and 144 distinct, and the 288 `own.` rows of their sources changed to count them). Every best set is now at least as good as the path after as many steps (33 comparisons in the full set, 7 in the sample). A limit that stays: each candidate is classified against the owned set the session starts with, and the tier modes offer one candidate per key, so a set does not reach the orders in which a path makes a later candidate of the same key new because an earlier one used the last copy of the lower tier it would have upgraded; with two candidates of one key a set could be worth less than the path.
- 2026-10-16 The engine's data travels as the shards do: the bundle of a trio and the item table are result files of the precompute, never committed. A run writes `<trio>/engine-l<level>.json` (`export.browser.bundle`) and `<results>/items.json` (`export.browser.items`, one file for the folder) from the catalog document it was given and the private seen flags it was given, so that their evidence levels are the ones the shards were solved with: a seen item is strict in the item table, and in the pools the bundle's weapon setups of each level are read from, unless a patch or research removal hides it. Nothing in either file says that a flag was merged (no reason code, no hash). The files are made at the start of the run, checked against what the run read for itself (the usable items of the trio and their levels; the bundle's setups against the grid's), and written with the shards (the item table first; an identical one is left alone, another is replaced whole and the run says so). A file that cannot be made (a pool whose weapon setups depend on the race, an item the tier rules cannot read) is a violation of the run, as an oversized shard is, not a stop. The module that holds the rule of the levels (`precompute/grid.py`) is hashed into the fingerprint of the chunks and was not touched. The site build reads both through `site/data.py` (the format number, the trio, the level, the release and the rules version of the shards, the exporter's own reader on the bundle, every item a shard shows against its record), publishes them byte for byte under `assets/engine/data/` as `items-<HASH>.json` and `<trio>-l<level>-<HASH>.json` (the first 16 digits of the SHA-256, in capitals) and lists them in `engine-manifest.json`, which is version 2: `"items"` and, for each trio, `"bundles"` beside `"levels"`, a bundle for each level and for no other, each with its SHA-256 for the worker to check before it parses a byte. (The bundles were moved out of the main manifest into a manifest for each trio; see the entry on the engine's manifests below.) Budgets, enforced by the build and named in its errors: a bundle 64 KB raw, the item table 4 MB raw and 512 KB gzip (the real item table of PAL/MNK/BER's catalog is some 1.9 MB and 182 KB gzip, a bundle 21.6 KB). The data files carry no `license` or `attribution` of their own, since the bundle's and the table's formats are exact and the footer of every page carries the one attribution; the item names in the table are the wiki's, and a page that shows them says so.
- 2026-10-16 Equip now is the first scenario mode the worker answers. The test of the two builders over the same scenarios that the entry of 2026-10-14 asked for is the Equip now answers of `fixtures/site/equip-now.json` (three scenarios, made by Python's `upgrade.equip_now` with the tie stage; the browser has none, and the owned sets are chosen so that the best kit is the same without it), which the worker's handler and a real browser are held to. - 2026-10-16 The engine's manifests: the main manifest lists no bundles, and each trio has a manifest of its own. The first layout of `engine-manifest.json` (version 2) listed the bundles of every trio with their path, sizes and SHA-256, some 218 bytes a trio: for the planned 560 trios that is 122 KB at one level and 245 KB at two, and the page and the worker refuse a manifest over 64 KB (`LIMITS.maxManifestBytes` of `protocol.js`), so a full build passed and every optimizer was dead. Now `engine-manifest.json` holds the optimizer's files, the item table, the release of the data (`data_release`, `rules_version`) and, for each trio, only its levels (`"trios": {"pal-mnk-ber": [50]}`): 560 invented trios at two levels are 12.9 KB, some 22 bytes a trio. The bundles of a trio are in `engine-trios/<trio>.json` (`{version, data_release, rules_version, trio, bundles: {"<level>": {path, bytes, gzip, sha256}}}`, 457 bytes for such a trio at two levels), at a fixed address outside `/assets/`: like the main manifest it keeps the host's default caching and is asked for again on every visit, so `site/_headers` has no rule for it (the only caching rule matches `/assets/*`, and a test says that no rule of caching matches either manifest). The worker makes the address only from the name of a trio that the main manifest lists, never from the text of a request; it reads the file with a size limit of its own (8 KB, `LIMITS.maxTrioManifestBytes`), as strictly as the main one (only the fields it lists, level names without a zero in front, in the key and in the file name of the bundle, so that "50" and "050" cannot be one level twice; a bundle for each level the main manifest lists for the trio and for no other; a bundle whose file name carries its trio, its level and its digest), and refuses it if its `data_release` or `rules_version` is not the main manifest's. The build checks the main manifest and every trio manifest against the browser's limits (a build over a limit is a `BudgetError` naming the file) and a test holds the numbers of `build.py` to those of `protocol.js` and `manifest.js`; a test renders the manifests of 560 invented trios at two levels, and has the browser's reader read them. The version of the main manifest stays 2: its first layout never left the branch it was made on. The question that asks for consent names the download of the request: for a scenario it counts the item table and the bundle of the trio as well as the worker and the WebAssembly (the page reads the manifest of the trio before it asks: a few hundred bytes, no data); a question asked before any request counts the item table and no bundle, and a model request counts neither. The figure is for the first request: a later request for another trio fetches that trio's bundle, a few kilobytes, which it does not count. After a release the files that a live worker names are gone and the manifest of a trio is the new release's: when the data of a scenario fails to load, or the manifest of its trio is of another release than the worker's manifest, the page reads `engine-manifest.json` again, and if that is another text than the one it began with it shows the notice that the page has to be reloaded (`updated`) instead of an error.
- 2026-10-16 The time of a request to the engine, and its faults: the budget of a request is the time its solve may take, counted from the moment its data is in, and the page's watchdog gives a request a new window (its budget and five seconds) at every sign of life. The first Equip now downloads its data (the manifest of the trio, the item table, the bundle) inside the request. Counted from the arrival of the request, the budget of a request on a slow link was gone before the solver was called, and the watchdog, armed once for the budget and five seconds, stopped a worker that was only slow (512 bytes every 300 ms with a budget of a second: stopped at 6.0 s, twice, the item table fetched again each time). Now every report of progress of a request re-arms its watchdog (the post of the request is the first sign of life); the worker reports every second while it loads the data, whether bytes arrive or not (`LOADING_BEAT_MS`), so a worker that is waiting for a download is not taken for a hang; a download that has stopped is ended by its own stall rule (20 s with no byte, counted from the request, from the answer and from each piece: the answer re-arms it too) and not by the watchdog; and `elapsedMs` of the answer still counts the whole request. Faults are told by what they are. A `SolverFault` (a subclass of `SolveError`: HiGHS refuses a model the builder made, the run ends in a status the solve does not accept, the solution has an entry that is not a number or a column that is not whole) is `solver`, and the session that met it is closed. A bundle whose rules the engine cannot use is refused when it is loaded (its tier and weapon rules are compiled then, not at the first owned item) as `engine-load` and is not kept; a bundle that no session can be made of, and an item that the table writes so that it cannot be worked out, are `engine-load` with that data dropped, so that the next request fetches it again. What the visitor chose (a name the bundle does not have, an item the table does not have) stays `bad-request`.
